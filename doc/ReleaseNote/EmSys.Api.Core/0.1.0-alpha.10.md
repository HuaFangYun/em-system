# EmSys.Api.Core 0.1.0-alpha.10

Date: 2026-10-11
Previous: 0.1.0-alpha.9

## Summary
Adds a versioned object storage engine, enabled by the host with builder.AddObjectStorage(). Modules store and read objects in buckets through IObjectStore, administrators manage volumes, policies and buckets through IObjectStorageServices, and objects in public-read buckets are served at /store. A database script must be installed before the engine is enabled.

## New features

- `EmAppBuilder.AddObjectStorage()` registers `IObjectStore` (scoped), the `IObjectStorageServices` actions, the claims `Object Storage Manager Access` and `Object Storage Settings Manage`, background maintenance and the public `/store` path. Object storage is off unless the host calls it; calling it twice throws.
- Buckets hold objects; every upload is a new version (versioning is always on). Delete adds a delete marker, restore adds a new version pointing to older content, and purge permanently removes one version. Bucket names and key limits follow S3 rules; keys are case-sensitive and never become file paths.
- Content is stored once per SHA-256 (global deduplication across buckets) and copied to one or more **volumes**. Version 1 supports `LocalFolder` volumes (a local disk or mounted share) with the states `Active`, `ReadOnly` and `Offline`.
- **Policies** per bucket: ordered volume list, minimum and target replicas (up to 16), version retention by count and age, quota of logical bytes and of objects, maximum object size and `Private`/`PublicRead` access. Volumes, policies and buckets are stored in the database and take effect without a restart.
- `IObjectStore` for modules: `PutAsync` (streamed, hashed while written), `OpenAsync` (seekable stream of the current or a given version), `GetAsync`, `DeleteAsync`, `RestoreAsync`, `PurgeVersionAsync`, `ListAsync` (prefix, `/` delimiter, continuation token) and `VersionsAsync`. Errors are `ActionException` with 400, 404, 409 (quota or read-only bucket), 413 (object too large) or 503 (not enough active volumes or no readable copy).
- `ObjectStoreBinaryStorage(IObjectStore, bucket)` implements `IBinaryStorage` on one bucket (no overwrite; delete purges every version). It is not registered automatically.
- Public read endpoint `GET`/`HEAD /store/<bucket>/<key>` for `PublicRead` buckets, without identity, with range requests, `ETag`, `If-None-Match`, `Last-Modified`, `X-Content-Type-Options: nosniff` and a sandboxing `Content-Security-Policy`. Everything else answers a plain 404.
- Maintenance: background replication (after uploads and at least hourly), version retention every six hours, and on-request garbage collection (review first, grace period 1–720 hours, default 24), retention and repair runs. Runs appear as business tasks (`objectstorage:gc`, `objectstorage:retention`, `objectstorage:repair`).
- Staging files from interrupted uploads are removed at startup; no version ever points to content without a ready copy.

## Upgrade notes

- Before enabling `AddObjectStorage()`, run `doc/sqlscript/mssql/tables/060-objectstore.sql` (after `010-core.sql`) and then `doc/sqlscript/mssql/views/vi_StoreBucket.sql`, `vi_StoreObject.sql` and `vi_StoreVolume.sql`. All scripts can be run again safely. Startup fails with a clear message when they are missing.
- Object storage requires SQL Server for the core database and assumes one API instance per database and volume set; a second instance only produces a logged warning.
- Existing CDN, container registry, NuGet server and approval storage are not moved; no data migration is needed.
- No new package dependencies.
- Not included in this version: the S3 protocol, presigned URLs, remote volume providers, per-bucket user rights, multiple API instances, encryption at rest and automatic rebalancing.
- Guide: `doc/engine/engine-object-storage.md`.
